Make the agent survive a crash

A run becomes a job in a queue. Kill a worker in the middle of booking an interview, start another, and it finishes the run with exactly one application, one booking and one message.

0Before you start

Day 3 continues the Day 2 project. The tools, the agent loop and the memory are finished for you. Today the agent stops being a function you call and becomes a job that survives a crash. Python 3.10 or newer; nothing else to install.

Two databases, on purpose

fileholdswhy apart
agent.dbthreads, messages, runs, steps, tool calls, and now the job queueThe agent's own state. Can be replayed, trimmed or rebuilt.
placement.dbstudents, drives, applications, slots, notifications, and now the idempotency keysThe college's facts. A side effect and the key that guards it must commit together, so the key lives here.

What is in the kit

1A run is a job 70 minutes

A question goes into a queue. A worker claims it, keeps a lease on it, and a dead worker's runs go back into the queue.

1.1

Read the status machine

10 min

Open schema/agent.sql and find the run table. The new columns are the whole design.

columnmeaning
attemptsHow many times a worker has claimed it. max_attempts is the limit.
available_atUnix time; not claimable before this. Retries wait here.

1.2

enqueue

10 min

RunStore.enqueue(thread_id, text, model, max_attempts=3) saves the user's message and a queued run for it, in one with self.transaction(). A message without a run is a question nobody will ever answer; a run without its message has nothing to answer.

enqueue
InsertsThe message via self.append_message, then a run: new uuid4 id, status queued, the model, max_attempts, available_at = self.clock().
ReturnsThe run id.
FailureIf either insert fails, neither may remain.

the enqueue tests pass.

1.3

claim_next

20 min

The heart of the queue. Two workers polling at the same moment must never get the same run. Find the run and take it inside one with self.transaction(). That transaction starts with BEGIN IMMEDIATE, so it holds the write lock from the first statement: the second worker waits its turn instead of reading the same row.

claim_next(worker_id, lease_seconds)
FindsStatus queued and available_at <= now, oldest available_at first, then oldest created_at.
SetsStatus running, lease_owner, lease_until = now + lease_seconds, attempts + 1, started_at if still empty.
ReturnsClaimed(run_id, thread_id, attempts) with the new attempts, or None.

Why BEGIN IMMEDIATE and not BEGIN? A plain BEGIN starts by reading. Two workers that both read and then both try to write each wait for the other: the deadlock from Day 2. SQLite breaks it by failing one of them with "database is locked". Taking the write lock first is lock ordering, applied at the start of the transaction.

the claim tests pass, including two workers on separate connections.

2Idempotency keys 40 minutes

The retry unit is the tool call. A replayed call with the same key returns the stored result instead of acting twice.

2.1

Watch it fail first

5 min

The drill starts a worker, kills it with no warning right after it sends a notification but before it records doing so, starts a second worker, and counts. Right now it ends with notifications 2. Worker-B couldn't tell that the step had already happened, so it did it again. Every later part of today fixes some version of that.

you have seen FAIL, and can say which record was missing when worker-A died.

2.2

canonical_json and idempotency_key

10 min

A key must be the same every time the same call is replayed. Hashing gives a fixed-size fingerprint, but it compares bytes, not meaning, so first give every meaning one spelling.

in app/idempotency.py
canonical_json(value)json.dumps with sorted keys and no spaces. Whole floats become integers, including inside nested dicts and lists: Gemini sends 12.0 for an integer, and 12.0 and 12 must hash the same.
idempotency_key(run_id, step_seq, tool_name, args)SHA-256 hex digest of canonical_json([run_id, step_seq, tool_name, args]).

the key tests pass.

2.3

PlacementDb.once

15 min

once(key, tool_name, effect) runs effect at most once per key. Everything happens in one with self.transaction() as conn:, so the side effect and its key commit together or not at all.

If effect() raises, let it raise. The transaction rolls back, so the half-written effect vanishes and no key is stored. Catching the exception inside the transaction would commit half a side effect and promise it happened.

the once tests pass.

2.4

call_tool, then the drill again

10 min

In app/runner.py, call_tool must send side-effect tools (name in tools.SIDE_EFFECTS) through placement.once(key, name, lambda: tools.call(name, args)). Read-only tools call directly. Keep the try/except outside once.

Then read rebuild() and execute_run() in the same file. rebuild turns recorded steps back into what the model saw, and finds tool calls the model asked for that have no recorded result. Those run again, at the same step number, so they get the same key.

every Part 2 test passes and the drill prints PASS.

3Safe side effects 60 minutes

Make each side effect safe to repeat on its own: a conflict is a success, a lost race is normal, a duplicate message is dropped.

3.1

A duplicate application is a success

15 min

A key protects one step of one run. It can't help when the student asks "apply me to Zoho" again tomorrow, in a new run with new keys. The side effect itself has to be safe to repeat.

PlacementDb.create_application(student_id, drive_id)
DoesINSERT ... ON CONFLICT (student_id, drive_id) DO NOTHING. If no row was inserted, look up the existing one.
Returns(application_id, created). The tool already turns created = False into "already_applied": true, a success.

the application tests pass.

3.2

Optimistic locking for slots

15 min

The tool reads the slot's version, then asks to book it. Between the read and the write, another student might book it. Put the check in the WHERE clause, not in Python, so read-then-write can't be interleaved.

PlacementDb.claim_slot(slot_id, student_id, expected_version)
DoesUPDATE ... SET student_id = ?, version = version + 1 WHERE id = ? AND student_id IS NULL AND version = ?, in one statement.
ReturnsTrue if that statement changed a row. False is a normal outcome: the tool reports slot_taken with the remaining slots.

the slot tests pass.

L2

Retry, back off, dead-letter

20 min

fail_attempt currently marks every failure final. A rate limit is not final; a model that fails every time must not be retried forever either.

failurenew status
not retryablefailed, with finished_at
retryable, attempts < max_attemptsqueued, available_at = now + backoff_seconds * 2 ** (attempts - 1): 2 s, then 4 s, then 8 s
retryable, attempts used updead, with finished_at

Always record the error_code, clear the lease, and act only if this worker owns the run.

the dead-letter tests pass.

L3

Write the race test

25 min

tests/test_lab3_race.py is a spec, not a test. Delete its skip line and write the two tests its docstring describes: two workers with two runs booking one slot, and eight threads claiming the slot at the same instant with a threading.Barrier. Each needs its own database connection; one connection shared between threads proves nothing.
