Build the Placement Assistant

Five tools, a small agent that uses them, and a memory that survives a restart. By the end of the day you can ask it placement questions in plain English and see every step it took.

1Tools, 70 min2Agent, 40 min3Memory, 60 min4Lab, 90 min

Tick each "Done when" box as you finish a task; the bars fill as you go. Ticks stay in this browser only.

0Before you start

You need Python 3.10 or newer and your Gemini API key from Day 1. Nothing else: the placement data lives in memory, and the agent's memory in Part 3 uses SQLite, which comes with Python.

What is in the kit

Every test uses a scripted model, so running tests never spends your Gemini quota. The chat script spends quota only when you leave off --mock.

1Tools 70 minutes

Two sample tools are given. You build three more, following their patterns.

1.1

Read the given code

10 min

Read three short files in this order before touching the tools.

app/domain.py holds the objects your tools receive. app/data.py holds the placement data and the methods that read and change it: the only way a tool touches data. app/tools/dispatch.py turns a model's call into a Python call and already fixes the classic mistakes, like the model sending 12.0 for an integer.

you can say, without looking, which method in app/data.py returns a drive's rules.

1.2

Study the two sample tools

20 min

Open app/tools/placement_tools.py. Two tools are complete, one of each kind, and your instructor live-codes the first. Every pattern you need for your own tools is in them.

samplewhat to copy from it
check_eligibilityRead-only. The rule lives in data and _evaluate reads it. Failures are returned as a code plus a hint, never raised. Every failed rule is reported, so the model explains the verdict instead of deciding it.
apply_to_driveSide effect. Checks run in a fixed order and stop at the first failure. Eligibility is re-checked because an instruction asks but code enforces. The result carries what the next step needs: the free interview slots.

Now read their docstrings. The model never reads your code; the name, the description and the parameters are the whole interface. Both samples follow five rules:

  1. One job, verb_noun name. If the name needs "and", it is two tools.
  2. Say when, when not, and what changes. Name the intents that should trigger it, point to the sibling tool for near-misses, and state any side effect.
  3. Constrain every parameter. Format and an example for each. Ask for ids the model got from another tool, never free text.
  4. Return what the next step needs. Say what comes back and what to do with it.
  5. Errors are instructions. Tell the model how to recover.

The tests check what a machine can: at least 150 characters, every parameter named, Read-only in read tools, Side effect: in tools that write, and no TODO left. Whether a description actually steers the model, you find out in 2.3 and prove in lab 1.

the sample tests pass, and you can explain why apply_to_drive re-checks eligibility.

2A small agent 40 minutes

Put your tools behind a loop, then talk to it.

2.1

run_tool: a tool call that never crashes

10 min

In app/agent.py, run_tool(name, args) calls self.tools.call(name, args) and must never raise. A failure becomes a result the model can read and recover from. That is Day 1's self-healing, moved to where it belongs.

when the tool...return
returns normallyits result, unchanged. Bad arguments and unknown tools already come back as invalid_arguments and unknown_tool from dispatch.
raises NotImplementedError{"error": "not_implemented", "hint": "..."}
raises anything else{"error": "tool_failed", "hint": "..."}
Name the exception type in the hint, not its message.

the unfinished-tool and crashing-tool tests pass.

2.2

ask: the agent loop

20 min

ask(text) is one user turn. You wrote this loop on Day 1; this time it records a trace as it goes, because Part 3 saves exactly those steps.

details the tests check
contentsUser: {"role": "user", "text"}. Model: {"role": "model", "text", "raw": turn.raw}, plus "tool_calls": [{"name", "args"}] when it called tools. Always pass raw back: Gemini needs it.
traceModel step: {"step", "kind": "model", "tokens_in", "tokens_out"}. Tool step: {"step", "kind": "tool", "tool", "args", "result", "ok", "ms"}. Steps are numbered 1, 2, 3 across both kinds. Add entries with self._log(entry).
historyself.contents is kept between calls to ask: the model is stateless, so every call resends the whole conversation.
errorsAn AgentError from the provider passes straight through to the caller.

every agent test passes.

2.3

Talk to your agent

10 min

scripts/chat.py puts your loop and your tools in the terminal and prints every tool call, so you can see which tool the model chose and what your code returned.

Try "What's on my record?", "Am I eligible for Zoho?", "Apply me to Zoho", then "Book the first slot". When the model picks the wrong tool, the fix is in a description, not in the loop.

each of your three tools fires from a plain-English question at least once.

3Memory 60 minutes

Give the agent a memory that survives a restart: a schema, the SQL behind it, and the wiring.

3.1

Design the memory schema

20 min

On Day 1 the agent's memory was a Python list that vanished when the program stopped. First on paper, with your neighbour: what entities are hiding in it? Is the unit of work a message, or something bigger? Write your answers in docs/part3_design.md.

Then finish schema/agent.sql. The thread table is given as the pattern. Every column is NOT NULL unless the table says otherwise, timestamps default to strftime('%Y-%m-%dT%H:%M:%fZ', 'now'), and every → is a REFERENCES.

tablecolumnsconstraints
messageid INTEGER PRIMARY KEY, thread_id TEXT → thread, seq INTEGER, role TEXT, text TEXT, created_at TEXTUNIQUE (thread_id, seq)
role IN ('user', 'model')
runid TEXT PRIMARY KEY, thread_id TEXT → thread, status TEXT, model TEXT, tokens_in and tokens_out INTEGER default 0, error_code TEXT null, started_at TEXT, finished_at TEXT nullstatus IN ('running', 'succeeded', 'failed')
run_stepid INTEGER PRIMARY KEY, run_id TEXT → run, seq INTEGER, kind TEXT, tokens_in and tokens_out INTEGER default 0, created_at TEXTUNIQUE (run_id, seq)
kind IN ('model', 'tool')
tool_callid INTEGER PRIMARY KEY, run_step_id INTEGER → run_step, tool_name TEXT, args TEXT (JSON), result TEXT (JSON), ok INTEGER, latency_ms INTEGER, created_at TEXTrun_step_id UNIQUE: one call per step
ok IN (0, 1)

Two things to notice. A tool call is something the agent did, not something anyone said, so it lives under run_step and role has no tool value. And nothing about students, drives or applications belongs in this file: the agent's memory stays apart from the placement data it acts on.

the schema tests pass.

3.2

ConversationStore: the SQL

25 min

Six methods in app/memory.py. The connection is in autocommit mode, so each statement commits on its own unless you wrap statements in with self.transaction() as conn:, which is given.

methoddoes
append_message(thread_id, role, text)Insert with seq = the thread's highest seq + 1, computed inside the same INSERT. Return the seq.
load_history(thread_id)[{"seq", "role", "text"}] in seq order.
start_run(thread_id, model)New run, uuid4 id, status running. Return the id.
record_model_step(run_id, seq, tokens_in, tokens_out)Insert a model step and add its tokens to the run. One transaction.
record_tool_call(run_id, seq, name, args, result, ok, latency_ms)Insert a tool step and its tool_call, with args and result as JSON. One transaction. Return the step id.
finish_run(run_id, status, error_code=None)Set status, error code and finished_at.

One test makes the second insert fail on purpose and checks that the first one was rolled back too. Always use ? placeholders; never build SQL with f-strings.

the store tests pass.

3.3

An agent that remembers

15 min

Wire the store into Agent. Everything is optional: when self.memory is None, the agent behaves exactly as in Part 2 and those tests must still pass. The rule is write as it happens: if the program dies after apply_to_drive succeeds, the database must still show which run did it and why.

wherewhat to save
__init__Start self.contents from memory.load_history(thread_id).
start of askSave the user message, then start_run.
every model steprecord_model_step, before looking at the tool calls.
every tool steprecord_tool_call, right after the tool returns.
the answerSave the model's reply, then finish_run("succeeded").
AgentErrorfinish_run("failed", e.code), then re-raise.

all memory tests pass, and a restarted chat remembers what you said.

4Lab 90 minutes

On your own. If time runs short, do L2 and L3 first; they are the quickest to finish.

L1

A tool that fires once

35 min

Implement notify_student(student_id, message). It checks the student exists, rejects a message that is empty or longer than 160 characters with invalid_message, calls self.notifier.send(student_id, message) and returns {"notification_id", "status": "queued"}.

The code is the easy half. The real task is the description: it must fire on exactly one of four prompts. Edit PROMPTS in scripts/ab_descriptions.py to four of your own, three of which sound close but should not send anything. Run it, rewrite the description, run it again.

the lab 1 tests pass and docs/lab1_ab.md shows your final description firing 3/3 on its prompt and 0/3 on the other three.

L2

Prove append-only

20 min

In schema/append_only.sql, make SQLite itself refuse UPDATE and DELETE on message, whichever program connects. A rule in your Python code does not count. Look up CREATE TRIGGER ... BEFORE UPDATE and RAISE(ABORT, ...).

the append-only tests pass.

L3

Read history page by page

25 min
page_messages(thread_id, after_seq=0, limit=20)
Returns(items, next_after). items are {"seq", "role", "text", "created_at"} with seq > after_seq, in order.
next_afterThe after_seq for the next page, or None on the last page. When the count is an exact multiple of limit, the last full page already returns None: fetch limit + 1 rows to find out.
QueryWHERE seq > ?, no OFFSET. A message added between two calls must not shift or repeat anything.
limitBelow 1 raises ValueError.

the pagination tests pass.
